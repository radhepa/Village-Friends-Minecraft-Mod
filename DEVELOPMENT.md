# Village Friends handoff

Plains villages are procedural and art-directed: a random town centre ringed by the six guaranteed civic buildings, terrain-following streets, and lots filled with homes, vanilla-trade workshops, farms and small decorations. Keep every building an independent template with its own blueprint; improve one without touching the others.

Read [BUILDING_EDITING.md](BUILDING_EDITING.md) before changing structures. It documents the village graph, design kit, lot contract, simulation and gallery.

- Design programs: `tools/village_design/buildings/*.py` (shared helpers in `kit.py`, `parts.py`, `roads.py`). `python tools/design_village.py <name>` writes the blueprint; it never overwrites a hand-edited blueprint without `--force`.
- Building source for the compiler: one layered JSON file per template in `tools/village_blueprints/`.
- Village graph, pools, weights, processors, depth and distance: `tools/village_layout.json` (format 2).
- Compiler: `tools/create_village_structures.py`. Keep geometry in the designs/blueprints, not in this compiler.
- Runtime templates: `src/main/resources/data/villagefriends/structure/village/*.nbt`; pools under `worldgen/template_pool/village/`.

To improve an existing building, edit its design (or blueprint) under the same name and run:

```text
python tools/design_village.py tavern
python tools/create_village_structures.py --check
python tools/create_village_structures.py --only tavern
```

Lots keep one north-facing `villagefriends:building_entrance` jigsaw at `[x,1,0]` (air replacement, aligned joint, empty pool). Civic slots are at most 17 wide (large) or 11 wide (small). Preserve accessible enclosed bedrooms (`b.room`) and matched bed halves; doors need two clear blocks on both sides (the kit checks this). The catalog and tests derive required pools from the layout, so replacement filenames need no Java edits. Use `python tools/village_design/simulate.py` to balance pool weights, and `gradlew.bat runClientGameTest -PvillageGallery -Pgallery=name1,name2` to screenshot templates and whole villages in Minecraft.

Use the existing build target; changing Minecraft versions is separate work. `build.ps1` selects the installed user JDK and builds the mod. `gradlew.bat runClientGameTest -PstructuresOnly` validates structures in Minecraft; the default gameplay command runs all registered tests. Test code belongs in the gametest source set and is excluded from the release JAR.

The registry/items and village layout phases are implemented. Version 2.7 replaced the old outfit engine and all of its voxel garments with a Sims-style wardrobe in palette-locked pixel art with textured 3D pieces; read [OUTFIT_ENGINE.md](OUTFIT_ENGINE.md). Version 2.8 grew it to thirty hairstyles, thirty tops and thirty bottoms. Version 2.11 split it into men's and women's sets: men 80/120/120 and women 50/60/60, plus locked one-piece outfits and a denim material role. New clothing should stay casual medieval, except the men's plain *supreme casual* line (t101–t120, b101–b120). New hair should stay anime-inspired but grounded (no Goku/Vegeta spikes). Each piece is one Python module in `tools/wardrobe/`; read [WARDROBE_EDITING.md](WARDROBE_EDITING.md) before editing them, then run `python tools/wardrobe/wardrobe.py` (or `--only <id>`) and `--check`. Never hand-edit the compiled PNG/JSON under `assets/villagefriends/wardrobe/`. Every module declares its `gender`. Tops and bottoms mix freely within a set, except where tags forbid it (armor, hose, kilt, sandals) or a top and bottom are `locked_to` each other. Shared shapes live in `tools/wardrobe/kit.py` (garments) and `anime.py` (hair), with set extras in `kit_male.py`, `kit_female.py`, `kit_casual.py`, `anime_male.py` and `anime_female.py`. Outfit templates are per set in `tools/wardrobe/outfits/`, and every top must be in one. Use `gradlew.bat runClientGameTest -PoutfitsOnly` for focused renderer verification and screenshots, and `-PresidentSample` for five random men and five random women. Names remain editable in `tools/name_pools.json` (version 2: separate `male`, `female` and `unisex` lists per pool, optional pool `surnames`); keep Indian names and surnames in the `indian` pool, which is limited to complexions 2–5, and run `python tools/import_resident_names.py` to check and package them. `src/main/resources/villagefriends/legacy_names_v1.json` is the frozen pre-2.18 data used to keep old names that still fit; never edit it.

Version 2.6 adds restrained resident walking and articulated eyes. Read [ANIMATION_EDITING.md](ANIMATION_EDITING.md) before changing them. Both resident and armor models share the same gait function; keep special vanilla poses and original face UV colors intact. The Village Life animation pack adds clips residents choose for themselves (idles, work, hobbies, chats, greetings, reactions). Each clip is keyed in Python under `tools/animations/village_life/`; read [ANIMATION_PACKS.md](ANIMATION_PACKS.md), then run `python tools/animations/animations.py` and `--check`. Never hand-edit the compiled `resident_animations/*.json`. Use `-PanimationPack` for focused in-game verification.

Version 2.13 adds village life: a per-village census of residents, families, relationship meters, slow romance and news (`dev.villagefriends.social`, kept in step by `VillageSocieties`), ten friendship levels, Tomodachi Life–style speech bubbles, a rebuilt conversation window and the Village Ledger. Read [VILLAGE_LIFE.md](VILLAGE_LIFE.md) before changing them. The social model is pure and unit-tested; keep world access in `VillageSocieties`. Regenerate the bubble sheet and ledger art with `python tools/social_assets.py --preview`. Use `-PvillageLifeOnly` for focused in-game verification.

Version 2.14 adds village days: personal daily routines and weather behavior (`routine/Routine.java`, pure and unit-tested, applied by `ResidentRoutines` through vanilla's own activities), workstations that do something (`WorkstationBlock`, `Workstations`; models and art from `python tools/workstations/workstations.py`, never hand-edit their JSON or PNG), and a dialogue bank of 5,898 pieces of handwritten dialogue in `tools/dialogue/` compiled by `python tools/dialogue/dialogue.py` (chosen by `talk/Talk.java`; questions and offers by `TalkWorld`). Read [VILLAGE_DAYS.md](VILLAGE_DAYS.md) before changing them. Use `-Ptests=WorkstationGameTest` for focused in-game verification.

Version 2.19 adds the tavern: residents lunch, sup and spend evenings there, choose seats by who is sitting where, sit on an invisible `Seat` entity, and are served course by course by the keeper and the cook (`dev.villagefriends.tavern`: `Patronage` is pure and unit-tested, `TavernSurvey` reads any tavern building through its structure piece, `Taverns` runs it from one `Taverns.register()` call and one hook in `ResidentRoutines`). Seating, tables, the hearth, standing room and the stage are found in the building, so redesigned and biome taverns need no Java. Tavern furniture comes from `python tools/tavern/furniture.py` and meal sprites from `python tools/tavern/sprites.py` (both with `--check` and `--preview`); the Tavern animation pack is a second pack in `tools/animations/tavern/`, previewed seated with `python tools/animations/tavern_preview.py`. Read [TAVERN.md](TAVERN.md) before changing them. Use `-Ptests=TavernGameTest` (and `TavernVillageGameTest` for a generated village) for in-game verification.

Version 2.20 adds birthdays and notice boards: a village calendar (`social/Calendar`) with a birthday for every resident, birthday parties in the routine (`Routine.Block.PARTY`) run by `Birthdays` with a party hat (`PartyHatLayer`), and notice boards whose notices are generated by the pure `quest/Postings` and run in the world by `VillageQuests` (board screen `NoticeBoardScreen`). Read [BIRTHDAYS_AND_NOTICES.md](BIRTHDAYS_AND_NOTICES.md) before changing them. The board model and art come from `python tools/notice_board/notice_board.py`, the new items and the hat texture from `python tools/celebration_assets.py`; never hand-edit their JSON or PNG. Use `-Ptests=CelebrationsGameTest` for focused in-game verification.

Version 2.22 adds children's games and curious children following players (`dev.villagefriends.play`: `Games` is pure and unit-tested, `Playground` runs the games from one `Playground.register()` call, one hook in `ResidentRoutines` and one line in `VillagerCompanionMixin`; the client side is `PlaytimeClient`). Game animations are `tools/animations/village_life/games.py` on the `play` trigger; the Leather Ball sprite is `python tools/playground/sprites.py`. Read [PLAYTIME.md](PLAYTIME.md) before changing them, and use `-Ptests=PlaygroundGameTest` for in-game verification.

Knight and Archer defense and saved combat progression are implemented separately from buildings; read [GUARDS.md](GUARDS.md) for targeting, equipment, levels and verification. `GuardProgress` and `GuardDamageLedger` hold pure balance/credit policy; `GuardProgression` owns server persistence and confirmed-death awards through the shared guard damage integration. Use `-PguardsOnly` for combat/progression and `-PcompanionsOnly` for follow/wait/rescue regressions. Patrol assignments and Command Desk controls, the spatial bed scanner, real-time medical treatment and seating remain future work. The existing block entity hooks are intentionally empty. See PHASE1.md, PHASE2.md, OUTFIT_ENGINE.md and VERIFICATION.md for scope and evidence.



Version 2.21 adds residents' pets: residents who want a cat or dog befriend strays, keep them (vanilla taming, with a `PetGoal` for following, resting and playing) and play scripted games (`pet/PetPlays.java`) acted out by `pet` resident clips and pet tricks posed on the vanilla models (`client/PetPoser.java`). Pet tricks are authored in `tools/pets/tricks.py` and previewed offline with `tools/pets/preview.py`; never hand-edit `pet_tricks/pets.json`. Read [PETS.md](PETS.md) before changing them. Use `-Ptests=PetGameTest` for focused in-game verification.
